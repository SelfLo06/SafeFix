# SafeFix v0.2 Design

> Status: design for review; no implementation plan is included here.
> Date: 2026-08-06
> Product: SafeFix, local Python + pytest Coding Agent Harness
> Previous release: v0.1.0 (the tag is immutable)

## 1. Design intent

SafeFix v0.2 remains a constrained repair harness, not a general coding
assistant. Its objective is to repair existing Python project failures against
a frozen pytest evaluation set. Test discovery/generation happens before the
repair session and is controlled by the Harness. The Repair Model can only
propose source patches; the Harness remains the only component that can write
repair code, run the full suite, update a checkpoint, roll back, or declare
SUCCESS.

The v0.1 invariants remain locked:

- the Harness owns the main loop and pytest is the objective success signal;
- after baseline creation, the active test manifest and F0 are immutable;
- Repair Model actions cannot modify tests or bypass Guardrail, HITL, path
  boundaries, credential rules, or full-suite evaluation;
- every landed repair patch is evaluated by the complete frozen test manifest;
- only a strict improvement updates best; same, worse, and incomparable
  results restore best;
- new failures are regression evidence and never enter F0;
- only the Harness can produce a successful session result.

The existing non-interactive CLI remains usable. v0.2 adds a guided TUI and an
optional test-preparation phase without adding WebUI, cloud service, arbitrary
shell execution, or a new agent framework. The design assumes the current
stdlib-oriented dependency policy; no dependency is required by this design.

## 2. Current v0.1 seams and minimum corrections

The current repository already has the required repair seams: SessionRunner,
Config, SessionState, TestRunner, FeedbackEngine, Guardrail,
ApprovalProvider, SnapshotStore, the five LLM-visible tools, and redacted
session artifacts. v0.2 extends these seams rather than replacing the loop.

| Existing contract | v0.2 rule | Reason |
| --- | --- | --- |
| StopReason.SUCCESS means objective pytest success | Keep it; NO_REPAIR_NEEDED is a display/artifact status only | Prevent a second success authority |
| REQUESTED is emitted by finish | Keep it for Repair Model stop requests; add OPERATOR_STOP for /stop | Make operator intent auditable |
| Existing tests are readable but not writable | Existing tests are always included when they exist; generated is valid only when no existing tests were detected | Resolve the source-mode conflict without selecting existing tests away |
| apply_patch is the sole repair write entry | Candidate tests are written only by a Harness-owned staging writer before baseline; Repair Model never receives that capability | Preserve the repair write boundary |
| TestRunner runs pytest with display-only arguments | v0.2 adds an internal frozen manifest; user display arguments cannot reduce it | Make accepted generated tests part of every full evaluation |
| One repair LLM endpoint/key is configured | Keep legacy base_url/model as Repair Model aliases; add independent Test/Review role settings and keyring entries | Preserve v0.1 CLI while enabling three roles |
| CLI approval can block in a prompt | TUI approval is a pending state handled at a READY boundary | Input must not interrupt LLM, patch, pytest, or EVALUATE |

An explicit generated-only run with an existing test suite is rejected as a
configuration error. This is the smallest consistent interpretation of the
higher-priority invariant that existing tests always enter the baseline.

## 3. Architecture

The system remains a single-process layered Harness with one authoritative
repair loop:

~~~text
CLI / TUI adapter
        |
        v
SessionController
  PROJECT_INTAKE
  EXISTING_TEST_DISCOVERY
  TEST_PREPARATION (optional)
  FREEZE_TEST_SET
  BASELINE
  REPAIR LOOP (existing SessionRunner semantics)
  FINAL_REVIEW (checkpoint)
  STOP + artifact
        |
        +-- TestPreparationService
        |     Test Model -> candidate staging -> static rules
        |     -> stability runs -> acceptance / Review Model
        |
        +-- FrozenTestManifest + TestRunner
        +-- Repair Model + ActionParser + Guardrail + tools
        +-- Review Model (checkpoint calls only)
        +-- EventSink / OperatorCommandQueue
~~~

SessionController may be implemented by extending the current SessionRunner,
but the preparation service and TUI adapter have separate responsibilities:

- TestPreparationService never calls Repair Model and never mutates
  production code or existing tests.
- FrozenTestManifest is created once immediately before the formal baseline.
- SessionRunner starts only after the manifest and F0 exist; Test Model is then
  closed for the session.
- Review Model is invoked only at preparation review checkpoints, large-patch
  risk summaries when requested, and final diff review. It never modifies
  files, generates tests, changes F0, or determines pytest success.
- CLI and TUI are front ends over the same controller; they do not duplicate
  repair policy.

## 4. Session phases and state transitions

~~~text
PROJECT_INTAKE
  -> EXISTING_TEST_DISCOVERY
  -> TEST_PREPARATION?        (only when generation is enabled)
  -> FREEZE_TEST_SET
  -> BASELINE
  -> REPAIR_READY / REPAIR_DISPATCH / EVALUATE
  -> FINAL_REVIEW
  -> COMPLETE or FINAL_REVIEW_GATE
  -> STOP
~~~

### 4.1 Intake and existing-test discovery

Intake validates the project path, Python/pytest availability, config, model
roles, keyring entries, path policy, and high-risk opt-in. The optional user
background is guidance only; an absent background is valid.

Before generating candidates, the Harness runs the existing test suite and
records collected existing test IDs and their PASS/FAIL/ERROR state. Existing
tests are not subject to Test Model or Review Model approval.

### 4.2 Test preparation

When generation is disabled, the discovered existing test set proceeds directly
to freeze. When enabled, Test Model receives production code, README, public
documentation, docstrings, type annotations, existing tests, and optional
operator guidance. Its output is a bounded list of candidates:

~~~text
GeneratedTestCandidate
- candidate_id
- test_source (one simple pytest test module or test case)
- basis (human-readable explanation)
- sources (project-relative source references)
- touched_existing_tests (must be empty)
~~~

The model output is parsed and validated at the LLM boundary. Candidate source
is placed in a session-specific Harness-owned staging directory, not in the
project's formal tests directory. The Repair Model cannot address this
directory through any tool.

Static rules reject candidates that use private implementation details,
unsupported exception guesses, performance thresholds, network/time/random
behavior, complex snapshots, excessive mocking, undeclared dependencies,
existing-test edits, or behavior without a concrete basis. Static rejection is
deterministic and does not call a model.

Each surviving candidate is run against the unmodified production tree for the
configured stability_runs (default 3). The Harness classifies results:

- stable PASS: every run is valid and the candidate passes;
- stable FAIL: every run is valid, the candidate fails, and its failure
  identity/signature is stable;
- ERROR: collection or infrastructure error;
- FLAKY: valid runs disagree in outcome or failure identity.

ERROR and FLAKY are automatically rejected. Candidate runs are isolated from
one another and cannot modify production code, existing tests, or the formal
baseline.

### 4.3 Acceptance modes

The default is standard. The supported modes are:

| Mode | Stable PASS | Stable FAIL | ERROR / FLAKY |
| --- | --- | --- | --- |
| review | manual approval | manual approval | reject |
| standard | automatic acceptance | manual approval | reject |
| high-risk | automatic acceptance | automatic only when every high-risk rule passes; otherwise manual | reject |

High-risk mode requires explicit CLI/TUI opt-in and a visible confirmation. A
config file alone cannot silently enable it. In non-TTY mode, high-risk mode is
rejected because v0.2 has no non-interactive auto-confirm path.

Automatic acceptance of a failing candidate requires all of:

1. clear, locatable documentation or user-behavior basis;
2. deterministic static-rule approval;
3. independent Review Model approval;
4. stable repeated results;
5. simple, local test structure;
6. no existing-test modification;
7. different Test and Review base_url + model values;
8. the configured automatic-failure limit has not been reached.

Failure of any condition downgrades the candidate to manual approval. The
Review Model may return only a structured approval/rejection and risk summary;
the Harness owns the acceptance decision.

### 4.4 Freeze and formal baseline

Accepted generated tests are copied into the Harness-owned generated-test
workspace and recorded alongside existing test paths in a manifest. The active
source is:

- existing: existing tests only;
- generated: generated tests only, valid only when no existing tests exist;
- mixed: existing tests plus accepted generated tests.

The manifest records path, content hash, origin, candidate ID, and acceptance
record. The Harness then runs the complete manifest, creates F0 from every
failed/error failure ID, and freezes both manifest and F0. The manifest is
verified before every later full evaluation. A mutation or missing test after
freeze is an infrastructure error, not a reason to silently redefine the
baseline.

The internal TestRunner may add only the manifest's exact test paths to its
pytest invocation. User-provided display arguments remain allowlisted and
cannot remove manifest entries or change collection scope. “Full pytest” in
v0.2 means the entire frozen manifest, not an arbitrary subset.

If the valid baseline is green, the session stops with SUCCESS and records
repair_required=false / display status NO_REPAIR_NEEDED. Otherwise Test Model
is closed and the existing Repair loop begins.

## 5. Three model roles and credential boundaries

Each role has independent configuration and keyring identity:

~~~text
ModelRoleConfig
- role: test | repair | review
- base_url
- model
- keyring_service
- identity_fingerprint (redacted, non-secret)
~~~

The legacy base_url and model fields remain aliases for the Repair Model.
Test Model settings are required only when generation is enabled. Review Model
settings are required for high-risk candidate acceptance and high-risk final
completion. For a legacy run with generation disabled and no Review Model
configured, final review is recorded as NOT_CONFIGURED and v0.1 behavior is
preserved; configuring Review Model enables the v0.2 checkpoint review.

The production credential source remains OS keyring only. Each role uses a
separate keyring entry. API keys never appear in TOML, environment variables,
logs, artifacts, prompts, or model identity fingerprints. Same provider with
different models is allowed but produces a warning; identical base_url + model
between any two roles is rejected.

## 6. Guided Repair Console (TUI)

The TUI is a guided console, not a chat surface. On a TTY it is the default
front end for a v0.2 run; the existing plain event-stream CLI remains available
through an explicit plain/no-TUI option and is always used for non-TTY input.
No TUI input can invoke a tool directly.

The screen shows:

- phase, step, round, and no-progress counters;
- baseline and current unresolved failures;
- best checkpoint summary;
- LLM-call and Harness-tool summaries;
- Guardrail decisions and approval state;
- patch file/line summary;
- pytest progress and result;
- rollback reason;
- Review Model verdict/risk summary;
- final StopReason.

The input reader writes to an operator command queue while the controller owns
the active operation. LLM calls, patch application, pytest, and EVALUATE are
not interrupted. At the next READY boundary:

- ordinary text is appended to the next Repair Model context as a bounded,
  redacted guidance event;
- /pause prevents the next LLM decision and enters PAUSED;
- /resume returns to READY;
- /status emits the current snapshot without changing state;
- /stop is consumed at a safe boundary, restores best, and ends with
  OPERATOR_STOP;
- /approve and /deny affect only an existing pending approval; otherwise they
  are no-ops with an explanatory event.

Guidance cannot write files, execute shell, change the manifest or F0, skip a
test, bypass Guardrail, or declare success. TUI rendering failures are runtime
errors; they do not grant the input channel extra authority.

The event protocol is a small typed record, not a general event bus:

~~~text
SessionEvent
- sequence
- timestamp
- phase
- kind
- safe_payload
~~~

Allowed event kinds are intake, test-discovery, candidate, stability-run,
acceptance, guidance, control, model-call, tool, guardrail, patch, pytest,
rollback, review, and terminal. Payloads contain summaries and identifiers,
never keys, complete source, or unredacted model responses.

## 7. Repair and final review behavior

After freeze, the Repair Model receives only the frozen failure summary,
approved operator guidance, current best summary, and existing read/search/
patch/finish tools. It cannot invoke Test Model or Review Model.

The current v0.1 patch rules remain unchanged: permanent deny precedes HITL,
large patches require approval, successful patches always run the complete
manifest, better updates best, and same/worse/incomparable restore best. New
failures remain outside F0.

For a large patch, Review Model may produce a bounded risk summary before the
existing human approval. It cannot approve the patch in place of HITL.

After a valid all-green evaluation, Review Model receives a checkpoint request
containing baseline summary, final diff summary, changed-file list, operator
constraints, and pytest result. It returns exactly one of:

- PASS: no material concern found;
- WARN: concern worth displaying but not a completion blocker;
- REVIEW_REQUIRED: human inspection is required by the review model.

In standard mode, pytest green always yields SUCCESS; WARN or REVIEW_REQUIRED
is displayed prominently and recorded. In high-risk mode, REVIEW_REQUIRED
enters a final human gate. The gate can accept the result or reject it.
Rejection restores the best checkpoint from before the final green candidate and
ends with FINAL_REVIEW_REJECTED; the Review Model itself never declares or
cancels objective pytest success.

## 8. Data contracts and artifact

The v0.2 domain additions are:

~~~text
BaselineSource = existing | generated | mixed
AcceptanceMode = review | standard | high-risk
CandidateStatus = PASS | FAIL | ERROR | FLAKY
ReviewVerdict = PASS | WARN | REVIEW_REQUIRED | NOT_CONFIGURED
Phase = PROJECT_INTAKE | EXISTING_TEST_DISCOVERY | TEST_PREPARATION |
        FREEZE_TEST_SET | BASELINE | READY | DISPATCH | EVALUATE |
        FINAL_REVIEW | FINAL_REVIEW_GATE | PAUSED | STOP
~~~

StopReason retains all v0.1 values and adds OPERATOR_STOP,
TEST_PREPARATION_ERROR, and FINAL_REVIEW_REJECTED. PAUSED, pending candidate
approval, and final review approval are phases/states, not terminal success
values.

The frozen manifest contains:

~~~text
FrozenTestManifest
- session_id
- baseline_source
- existing_test_paths and content hashes
- generated_test_paths, candidate IDs, and content hashes
- accepted/rejected candidate records
- stability_runs
- manifest_hash
~~~

The session artifact additionally records at least:

~~~text
baseline_source
existing_test_count
generated_candidate_count
generated_pass_accepted
generated_fail_accepted_manual
generated_fail_accepted_automatic
rejected_count
error_count
flaky_count
acceptance_mode
stability_runs
test_model_identity
repair_model_identity
review_model_identity
review_verdict
review_summary
guidance_event_summaries
high_risk_confirmation
baseline_manifest_hash
repair_required
stop_reason
~~~

Identity fields are provider/model fingerprints without credentials. Guidance
records bounded event summaries, not arbitrary full user text. Artifacts never
contain API keys, complete source files, or unredacted model responses.

## 9. Error and compatibility policy

- Invalid project/config/path/model-role/keyring setup stops before baseline
  with the existing configuration mapping.
- Candidate parse/static/stability rejection is a candidate outcome and does
  not change the formal baseline.
- Test Model transport or candidate staging infrastructure failure ends with
  TEST_PREPARATION_ERROR; it does not silently fall back to Repair Model.
- Invalid baseline or post-patch manifest/test infrastructure failure ends with
  the existing runtime/config error mapping after restoring the best valid
  checkpoint.
- Operator stop is safe-boundary only and restores best before returning.
- No new test is accepted after freeze, even if the Repair Model or operator
  requests it.
- The existing safefix run, credential commands, non-TTY deny behavior, path
  boundaries, pytest allowlist, and v0.1 stop/exit meanings remain compatible
  unless the user explicitly opts into v0.2 preparation/high-risk behavior.

## 10. Acceptance criteria for this design

The v0.2 implementation is conforming only if it can demonstrate, with mock
models and deterministic fakes:

1. existing tests are never edited or excluded silently;
2. candidate PASS/FAIL/ERROR/FLAKY classification is stable and repeated;
3. standard and high-risk acceptance rules are enforced by Harness code;
4. freeze prevents Test Model calls and test-manifest changes;
5. every repair patch still receives a complete frozen-manifest pytest run;
6. TUI guidance queues without interrupting atomic operations;
7. /stop restores best and cannot declare success;
8. standard and high-risk final Review behavior matches the stated gates;
9. artifacts contain the required counters and redacted role/review/guidance
   records;
10. the current v0.1 offline mechanism tests and non-TTY CLI behavior remain
    green.

## 11. Design self-review

- Marker scan: no unresolved marker or undecided option is present.
- Contradiction scan: generated-only semantics, SUCCESS versus
  NO_REPAIR_NEEDED, operator stop, Review Model authority, and full-suite
  manifest scope are explicitly resolved.
- Ambiguity scan: default acceptance mode, stability-run count, high-risk
  confirmation, role credential requirements, TUI command timing, and final
  review outcomes are explicit.
- Scope scan: no implementation plan, production code, dependency, WebUI,
  shell tool, dynamic post-freeze test generation, or automatic test editing
  is included.
