# SafeFix v0.2 Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Extend SafeFix with an isolated pre-baseline test-preparation phase, independent Test/Repair/Review model roles, a frozen test manifest, a guided TUI, final Review checkpoints, and auditable v0.2 artifacts while preserving every v0.1 repair-loop invariant.

**Architecture:** Keep SessionRunner as the single Harness authority. Add a typed preparation pipeline before baseline, a frozen manifest consumed by TestRunner, checkpoint-only Review calls, and a TUI adapter that communicates through a bounded event sink and operator command queue. The existing plain CLI remains a front end over the same controller.

**Tech Stack:** Python >= 3.11; existing stdlib, pytest, keyring, and OpenAI-compatible HTTP client only. No new dependency, WebUI, cloud service, shell tool, or agent framework.

## Global Constraints

- v0.1.0 tag is immutable and must not be rewritten.
- Root PLAN.md is the finalized v0.1 plan; this v0.2 plan is additive and lives at docs/superpowers/plans/2026-08-06-safefix-v0.2-implementation-plan.md.
- Read SPEC.md, PLAN.md, AGENTS.md, and the approved v0.2 design before every implementation task.
- Create an isolated v0.2 worktree before implementation using superpowers:using-git-worktrees.
- Use superpowers:subagent-driven-development, strict TDD, two reviews per task, verification-before-completion, and intentional commits.
- Existing tests are never modified or deleted by Test Model or Repair Model.
- If any collectible existing tests exist, generated-only is invalid; only existing or mixed may be used. Generated-only is valid only when no usable existing tests are collected.
- Candidate tests are staged only by Harness code before formal baseline; Repair Model apply_patch remains production-only and test-denying.
- Before formal baseline, candidates are classified PASS, FAIL, ERROR, or FLAKY using repeated stability runs.
- Default acceptance mode is standard: stable PASS automatic, stable FAIL manual, ERROR/FLAKY rejected.
- High-risk only increases pre-baseline failing-candidate automation; it cannot exclude existing tests, change F0, bypass Guardrail/HITL, skip pytest, or declare SUCCESS.
- Test/Repair/Review roles use separate keyring entries. API keys never enter TOML, environment variables, logs, artifacts, prompts, or fingerprints.
- Identical role base_url + model is rejected; same provider with different models is allowed with a warning.
- After freeze, the manifest and F0 are immutable; Test Model is closed.
- Every landed repair patch runs the complete frozen manifest. SUCCESS is Harness-owned and requires a valid all-green full result.
- better updates best; same, worse, and incomparable restore best. New failures never join F0.
- TUI input is queued and cannot interrupt LLM, apply_patch, pytest, or EVALUATE.
- TUI and new failure/review states must remain deterministic under fake clients and fake streams.
- No broad exception handling, speculative fallback, duplicate boundary validation, or configuration for hypothetical future providers.
- Every task ends with focused tests, relevant regression tests, a specification-compliance review, a code-quality review, verification evidence, and a commit recorded in AGENT_LOG.md.
