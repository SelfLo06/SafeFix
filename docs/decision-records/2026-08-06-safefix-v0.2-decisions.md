# SafeFix v0.2 前期产品决策记录

日期：2026-08-06
状态：Brainstorming 基本完成，待用户审阅正式设计文档后进入实现计划阶段

> 本记录保留关键决策及其理由；正式设计文档负责结构化系统边界、接口和验收规则。

## 1. 起点：是否增加交互式 TUI

当前 SafeFix 只有普通 CLI。讨论的第一个问题是，是否增加一个类似 Codex、但明显更轻量的交互式 TUI，以便用户查看运行阶段、测试、补丁、回滚和停止原因，并在运行期间提供输入、处理人工审批。

决定采用轻量 TUI，而不是 WebUI 或完整的 Codex 式通用界面。TUI 的定位是：

> Guided Repair Console，即面向受约束 pytest 修复流程的交互式控制台。

TUI 不能只是“更漂亮的 CLI”，也不能把 SafeFix 扩展成通用编程助手。

## 2. 对 SafeFix 产品定位的重新确认

SafeFix 不是：

- Codex 类通用 Coding Agent；
- 从自然语言开始开发新功能的系统；
- 可以自由执行 shell 的助手；
- 自动修改测试并自行证明成功的 Agent；
- 从零构建完整项目的工具。

SafeFix 是：

> 面向 Python 项目，以 pytest 为客观反馈信号，在代码边界、Guardrail、HITL、checkpoint 和回滚控制下修复生产代码的 Agent Harness。

因此，TUI 和新增模型能力都必须服务于修复流程，不能改变核心成功标准。

## 3. TUI 中用户输入的语义

讨论了三种输入模式：

1. 只有暂停后才能输入；
2. 输入框始终可用，输入排队，在下一个安全边界生效；
3. 像 Codex 一样随时对话并动态改变当前执行。

最终选择第二种，并进一步限制输入权限。

用户输入不是开放式聊天，而是：

> Operator Guidance，运行期间排队的人工修复指导。

规则如下：

- 输入框始终可用；
- 不打断正在执行的 LLM 请求；
- 不打断 apply_patch；
- 不打断 pytest；
- 不打断 EVALUATE；
- 只在下一个 READY 边界加入 Repair Model 上下文；
- 不能直接修改文件；
- 不能执行 shell；
- 不能修改测试；
- 不能改变 baseline 或 F0；
- 不能跳过完整 pytest；
- 不能声明 SUCCESS；
- 不能绕过 Guardrail。

控制命令：

- /pause
- /resume
- /stop
- /status
- /approve
- /deny

/approve 和 /deny 只在存在待审批动作时有效。

## 4. 初始错误如何获得

用户问题描述是可选输入，不是启动修复的必要条件。

SafeFix 默认自行运行 pytest，自动发现已有失败：

1. 用户提供项目目录；
2. SafeFix 读取配置；
3. SafeFix 运行已有 pytest；
4. 从测试报告中获得初始失败；
5. 建立 baseline；
6. Repair Model 根据失败反馈进行修复。

用户可以额外提供问题背景、预期行为、兼容性约束、代码范围提示和已知调试线索。这些信息只作为辅助上下文，不能替代测试结果。

## 5. 是否自动生成测试

陌生项目可能存在测试覆盖不足，因此增加可选的自动测试生成能力，但与修复循环严格隔离。

原因：

- pytest 是 SafeFix 的客观评价标准；
- 同一模型同时编写测试和修复代码会形成自我评分；
- 模型可能生成容易满足、错误或臆造需求的测试；
- baseline 建立后修改测试会破坏 F0 冻结、进展判断和回滚语义。

测试生成只能发生在：

> baseline 建立之前的独立 Test Preparation 阶段。

## 6. Baseline 的三种来源

SafeFix v0.2 支持三种 baseline 来源：

### existing

只使用项目已有测试。

### generated

只使用经检查和批准的生成测试。

### mixed

使用项目已有测试，加上经检查和批准的生成测试。

默认仍允许关闭测试生成，直接使用现有测试。对真实陌生项目，mixed 被认为是最实用的模式。

与 v0.1 不变量的兼容解释必须在正式设计中明确：已有测试不能被模型静默排除；如果项目存在已有测试，generated-only 不能绕过它们。

## 7. 三个模型角色

### Test Model

负责阅读生产代码、README、docstring、类型注解、公开接口和已有测试，生成简单候选 pytest 测试，并为每个测试提供行为依据。

禁止修改生产代码、修改或删除已有测试、直接改变正式 baseline，或参与生产代码修复。

### Repair Model

负责读取冻结后的测试失败信息，读取和搜索生产代码，提出受 Guardrail 限制的补丁，修复生产代码。

禁止创建、修改或删除测试，改变 baseline 或 F0，调用 Test Model 重新定义成功标准，或自行决定 SUCCESS。

### Review Model

负责独立审查，不负责执行修改。

可复用场景：

1. 审查准备进入 baseline 的失败候选测试；
2. 为触发 HITL 的大补丁生成风险摘要；
3. pytest 全绿后审查最终 diff；
4. benchmark 中评价补丁相关性、最小性、维护性和过拟合风险。

禁止生成测试、修改代码、调用 apply_patch、改变 baseline 或 F0、替代 pytest、独立宣布 SUCCESS，或绕过人工审批和 Guardrail。

## 8. 模型供应商和凭据隔离

三个角色使用独立配置和独立 keyring 凭据条目。

建议：

- Test Model、Repair Model、Review Model 最好来自不同供应商；
- 最低要求是被审查模型与 Review Model 不能使用完全相同的 base_url + model；
- 相同供应商但不同模型允许使用，但应产生警告；
- 不同供应商是推荐配置，不作为绝对硬编码限制；
- 模型身份脱敏记录到 session artifact；
- API key 不写入 TOML、环境变量、日志或 artifact。

## 9. 生成测试的范围

允许生成：

- 模块导入；
- 公开函数正常输入；
- 有明确依据的空值和边界输入；
- README、docstring 或类型合同声明的返回类型；
- 明确的数据结构；
- 明确的不变量；
- 对已有测试风格的简单补充。

禁止或默认拒绝：

- 模型猜测的业务规则；
- 无依据的异常类型；
- 私有实现细节断言；
- 性能阈值；
- 网络测试；
- 时间敏感测试；
- 随机测试；
- 不稳定测试；
- 大量 mock；
- 复杂 snapshot；
- 依赖未声明的第三方包；
- 修改已有测试；
- 为制造失败而编造需求。

候选测试先进入隔离区域，不能直接写入正式测试目录。

## 10. 候选测试验证与分类

Harness 先进行静态检查，再在未修改的原始代码上运行候选测试。候选测试分类为 PASS、FAIL、ERROR、FLAKY，并进行多次稳定性运行。

- PASS：当前代码上稳定通过，主要提供回归保护；
- FAIL：定义了新的待修复行为，风险较高；
- ERROR：测试自身不可用；
- FLAKY：结果不稳定，不适合进入 baseline。

ERROR 和 FLAKY 自动拒绝。

## 11. 默认测试接受策略

讨论了三个方案：

1. 所有生成测试都人工批准；
2. PASS 自动接受，FAIL 人工批准；
3. 高置信度 PASS 自动接受，其他人工批准。

最终选择：

> 标准模式下，稳定 PASS 自动接受，稳定 FAIL 必须人工批准。

原因：

- PASS 通常只记录已有行为；
- FAIL 会直接增加新的修复目标；
- 新失败不能仅由生成模型单方面定义；
- 该方案在安全性和自动化程度之间比较平衡。

## 12. 高风险自动化模式

增加显式开启的 High-Risk Mode。高风险模式只提升 baseline 建立之前的生成测试接受自动化，不能解除修复阶段的核心安全边界。

稳定 FAIL 候选只有同时满足以下条件时才能自动进入 baseline：

- 有明确、可定位的文档或用户行为依据；
- Harness 静态规则检查通过；
- Review Model 独立批准；
- 多次运行结果稳定；
- 测试简单且局部；
- 没有修改已有测试；
- Test Model 与 Review Model 不是完全相同配置；
- 未超过自动接受数量上限。

任何条件不满足时，降级为人工审批。

建议定义三个接受等级：

### review

- PASS 人工批准；
- FAIL 人工批准。

### standard

- PASS 自动接受；
- FAIL 人工批准。

### high-risk

- PASS 自动接受；
- 满足证据、Review 和稳定性要求的 FAIL 可自动接受。

高风险模式必须显式开启，并显示不可忽略的风险摘要，不能静默启用。

## 13. Baseline 冻结规则

测试准备阶段结束后：

1. 合并已有测试和经批准的生成测试；
2. 运行完整测试集；
3. 建立 baseline manifest；
4. 记录 baseline 来源；
5. 冻结测试集；
6. 冻结 F0；
7. 关闭 Test Model；
8. 启动 Repair Model。

冻结后禁止新增、删除或修改测试，禁止重新调用 Test Model 改变评价标准，禁止 Review Model 改变 baseline，禁止 Repair Model 修改测试，也禁止将新出现的失败加入 F0。

## 14. 修复循环继续继承 v0.1 规则

v0.2 不能破坏现有核心循环：

- Harness 自己组织上下文；
- 调用 Repair Model；
- 解析工具动作；
- 执行 Guardrail；
- 落地合法补丁；
- 自动运行完整 pytest；
- 根据失败集合判断 better、same、worse；
- better 更新 best checkpoint；
- same、worse 或 incomparable 回滚；
- 新失败不能进入 F0；
- 达到限制时停止；
- SUCCESS 只能由有效完整测试集全绿触发。

## 15. Review Model 的复用范围

确认 Review Model 不只用于测试生成阶段。

### Checkpoint 1：失败生成测试进入 baseline 前

审查测试行为依据、臆造风险和实现耦合。

### Checkpoint 2：大补丁触发 HITL 时

为用户生成风险摘要，但不代替用户审批。

### Checkpoint 3：pytest 全绿后

检查无关重构、对测试硬编码、公开 API 变化、兼容性风险、删除必要校验、调试代码残留和生成测试过拟合。

### Checkpoint 4：benchmark

提供主观质量评价，与客观测试指标分开记录。

Review Model 不在每个修复步骤中调用，避免它变成第二个 Repair Agent。

## 16. 最终 Review 策略

最终 Review Model 返回 PASS、WARN 或 REVIEW_REQUIRED。

最终采用标准模式和高风险模式不同的处理方式。

### standard 模式

如果完整 pytest 全绿，但 Review Model 返回 REVIEW_REQUIRED：

- Harness 仍返回 SUCCESS；
- TUI 显示醒目警告；
- artifact 记录审查风险；
- 建议用户检查 diff。

### high-risk 模式

如果完整 pytest 全绿，但 Review Model 返回 REVIEW_REQUIRED：

- 不直接完成；
- 停在人工最终确认门；
- 用户可以查看 diff 和审查意见；
- 用户确认后才完成。

原因是 high-risk 模式可能曾自动接受失败生成测试，因此最终需要额外人工闭环。

## 17. TUI 应显示的信息

TUI 显示：

- 当前阶段；
- step、round、no-progress；
- baseline 来源和失败数；
- 当前 unresolved failures；
- best checkpoint；
- Test Model、Repair Model、Review Model 状态；
- 候选测试分类和接受结果；
- LLM 工具动作摘要；
- Guardrail 决策；
- 补丁摘要；
- pytest 进度；
- better、same、worse；
- rollback 原因；
- HITL 状态；
- Review verdict；
- 最终 StopReason。

TUI 是展示和控制适配层，不复制或重新实现核心修复循环。原有普通 CLI 和非交互使用继续保留。

## 22. TUI 设计修订：scrollback-first 的 Rich + prompt_toolkit 控制台

日期：2026-08-06

Task 13 在启动前被暂停。暂停不是因为 Harness、pytest、baseline 或三模型
设计失效，而是原 implementation plan 将 TUI 锁定为 stdlib-only，而新的产品
方向需要更可靠的持续输入、终端输出协调和可读的运行 transcript。暂停时 Task 13
没有提交生产代码、测试、依赖或包配置修改；当前 worktree 保留原状，不执行 reset、
clean、自动回滚或擅自重写。

比较过三个方案：

- Textual 提供最完整的全屏终端应用框架，但会推动产品走向多面板仪表盘、屏幕切换和
  更重的 UI 生命周期；这与 SafeFix 的轻量 scrollback-first 交互不匹配，因此拒绝。
- Rich 能高质量呈现事件 transcript、状态摘要、pytest、diff、Guardrail 和审批
  语义，但不单独提供持续输入、历史、补全和输入保护。
- prompt_toolkit 擅长持续输入、命令历史、补全、快捷键、异步输入和后台输出不破坏
  输入缓冲区，但不应承担复杂展示。

最终选择：

> prompt_toolkit 负责输入和输出协调，Rich 负责集中渲染，形成接近 Codex CLI /
> Claude Code 的滚屏式 Guided Repair Console。

该选择取消 stdlib-only 约束，但严格只允许新增 prompt_toolkit 和 Rich 两项
运行时依赖；不引入 Textual、Urwid、Blessed、PyTermGUI、图片、字体或其他 TUI
框架。Harness、Runner、模型、Guardrail、TestRunner、artifact 和状态机仍不依赖
UI 库。TUI 保持 Adapter 地位：Harness 独占主循环、pytest、baseline/F0 冻结、
checkpoint、better/same/worse、rollback、HITL、StopReason 与 SUCCESS；所有输入仍
仅能进入 OperatorCommandQueue 或现有审批边界。

交互采用四个克制区域：简短当前状态、向上滚动 transcript、始终可用 operator input，
以及仅在审批或 final review 时出现的交互提示。普通文本仍是延迟到 READY 边界的
operator guidance；/pause、/resume、/stop、/status、/approve、/deny 保持已批准
语义。/stop 只能在安全边界由 Harness 处理并恢复 best；TUI 不得直接调用工具、修改
文件/测试/baseline/F0、执行 shell、跳过 pytest、绕过 Guardrail 或宣布 SUCCESS。

视觉采用深色终端、绿色主强调和轻像素风静态边框/状态元素。绿色用于 active、safe、
success 和 checkpoint；琥珀用于 warning/approval；红色用于 deny/failure/rollback；
正文、失败和 diff 以可读性优先。不得要求像素字体、Nerd Font 或 Powerline。优先
ASCII、常见 Unicode box-drawing 与块元素，并在 Unicode 不可用时回退普通 ASCII。

TTY 默认启用低频、可丢弃的 8-bit 风格动画：spinner、短阶段扫过、checkpoint 闪烁、
better 计数变化、rollback/DENY 提示、SUCCESS 勾选和 approval 提醒。新增
--no-animation。非 TTY、重定向、测试、TERM=dumb、低能力终端或该标志都会关闭
动画；关闭后所有语义状态仍完整输出。动画不得逐字流模型输出、高频闪烁、阻塞输入或
Harness、改变事件顺序、依赖真实 sleep、进入 artifact 或污染非交互日志。

并发边界采用 Harness worker thread、线程安全 SessionEvent 队列和 UI main thread。
prompt_toolkit 的安全 stdout 协调与 Rich 的集中渲染构成唯一终端写入边界，保证后台
事件不破坏正在编辑的输入行。非 TTY 不启动 prompt_toolkit，保持现有 plain CLI 和
fail-closed 审批。TERM=dumb、NO_COLOR、无 Unicode 和 UI 关闭/异常必须安全降级，
